# Workflow version 3: authoring progress

[Workflow phase index](README.md) | [Functional Design draft](phase_construction/functional-design.md)

## Purpose

Track the next authoring decisions and the decisions deferred to later work. This file records specification work, not the execution state of a Unit of Work.

The Functional Design contract remains a draft. A saved draft is not approval of all its contents.

## Agreed decisions

- Functional Design requires `unit-of-work.md` and `design.md` at `.kepler/units-of-work/<unit-id>/`.
- `unit-of-work.md` supplies the definition shared by all stages. Its required sections are Purpose, Scope, and Context. See the [section contract](phase_construction/functional-design.md#unit-of-work-definition).
- Functional Design requires Domain behavior, Domain model, Boundaries and interactions, and Design decisions and open questions in `design.md`. See the [section contract](phase_construction/functional-design.md#functional-design).
- Non-functional Requirements replaces Non-functional Design & Requirements. It requires `.kepler/units-of-work/<unit-id>/quality.md`.
- Applicable non-functional requirements include performance, availability, security, accessibility, compatibility, operability, and observability.
- Implementation Planning selects the technical solution before it divides the work into tasks. It produces a plan that represents tasks and dependencies as a graph. See the [stage boundaries](phase_construction/README.md#agreed-boundaries).
- [Implementation Execution](phase_construction/README.md#implementation-execution) is a unit-scoped Construction stage between Implementation Planning and Unit of Work Review. The orchestrator schedules independent, ready task implementations concurrently from the plan graph.
- Each task implementation contains a [Task coding loop](phase_construction/README.md#task-coding), followed by [Task Integration](phase_construction/README.md#task-integration). Code Generation and Code Validation are task-scoped stages inside Task coding. Task implementation and Task coding are contexts, not additional stages or stage-attempt identities. Do not generalize this structure to other phases or stages.
- Task coding completes only when required validation succeeds and no blocking findings remain. Task implementation completes only after integration and successful required checks on the combined result. Code Validation retains its full-suite and independent-feedback responsibilities. Task Integration also requires the project build and full application test suite against the combined candidate. Both must succeed under the unit lock before acceptance. Any additional integration checks and project-specific check configuration remain open.
- [Task Integration order and locking](phase_construction/README.md#integration-order-and-locking) follow prepare, check, then accept under one lock per unit. Read the current unit checkpoint after acquiring the lock. Hold it through candidate preparation, required checks, and acceptance. Failed or incomplete required checks prevent acceptance. This replaces the earlier short-update restriction for integration locks. The lock does not gate task admission, coding, validation, or integrations for other units. Exact lock implementation, ownership records, coordination across workspaces, and interrupted-lock recovery remain open.
- Construction's [return paths](phase_construction/README.md#return-paths) distinguish implementation changes, integration-only retries, and upstream invalidity. The orchestrator authorizes returns to coding. Integration-only retries remain within the current attempt. Task-local returns do not themselves start another Implementation Execution attempt. Independent loops continue while their inputs and contracts remain valid.
- For Construction's [unit-wide upstream revision](phase_construction/README.md#unit-wide-upstream-revision), the orchestrator stops new task admissions and active implementation work for that unit. End active Implementation Execution and task-stage attempts. Preserve work and evidence as history. Execute the revised upstream stages before starting new implementation attempts. Independent units continue while their inputs and contracts remain valid. Task-local corrections retain their existing return paths.
- Implementation Execution has a unit-scoped attempt containing task-scoped stage attempts. Task implementation and Task coding add no separate run floors. Completion of Implementation Execution requires complete task implementations and the checked integrated unit result, ready for Unit of Work Review. The structure does not introduce another requester approval gate.
- `kepler-architect` is the Functional Design owner and uses `kepler-design`. No other agent roles are defined for this stage.
- Supporting skills adapt structured questioning, domain modeling, and research from `kepler-grilling`, `kepler-wayfinder-domain-modeling`, and `kepler-wayfinder-research`. Their paths and artifact contracts must follow version 3. See [supporting skills](phase_construction/functional-design.md#supporting-skills).
- Self-review is implemented within `kepler-design` and performed by `kepler-architect`. It is not a separate supporting skill. External review occurs only when the requester asks for it.
- Functional Design requires explicit requester approval, recorded through the `kepler` CLI in JSON execution state and audit history. Exact fields and formats remain in SH06. See [review and approval](phase_construction/functional-design.md#review-and-approval).
- [CLI infrastructure](runtime.md) separates mostly immutable artifact identity frontmatter from dynamic JSON execution state and audit records. Agents and skills operate on execution state through the CLI, not direct file edits.
- This persistence decision supersedes earlier choices to store approvals and changing depth selections in artifact metadata. Approval authority, depth selection rules, and revision semantics remain unchanged.
- A [stage attempt](runtime.md#stage-attempts) is one execution of one stage for one Unit of Work, including internal correction loops. Self-review and repeated edits after failed tests stay within the attempt while corrections remain within that stage. A report or revision recommendation does not create an attempt. Each stage starts a new attempt when it executes again after reopening authorized by the orchestrator. Pauses, resumes, new agent sessions, and failed commands alone do not create new attempts. Keep previous attempts as history. Attempt ID formats and exact binding record formats remain open in SH06.
- [Attempt identities and scope limits](runtime.md#attempt-identity-and-active-scope) are distinct from Git checkpoints. Every attempt has a distinct identity. For a fixed unit/task/stage scope, allow zero or one active attempt. Paused or waiting attempts still occupy their scope until they end. Preserve this limit under concurrent starts without blocking unrelated scopes. Unit-wide work without a task uses its own unit/stage scope. Construction uses its agreed execution structure. Other scope relationships require their own phase and stage contracts.
- The [run floor](runtime.md#run-floor) is the applicable attempt identity for its scope. No separate verification-round boundary is defined within an attempt. Earlier-attempt evidence and approvals do not establish current completion. Late results retain their original attempt binding. Material applicability remains a separate check.
- [Git checkpoints](runtime.md#evidence-and-content-checkpoints) identify multi-file repository snapshots. Attempt identity is separate from commit identity. One attempt can reference several checkpoints, and different attempts can reference the same checkpoint. A commit does not establish passed checks or requester approval.
- [Material types](runtime.md#material-references) are open-ended. Examples include code, documents, MR/PRs, CI pipelines, container image versions, and logs retained locally or externally. Git identifies repository material; other material uses appropriate references. Retain relevant content or an immutable version when mutable references do not identify what was examined.
- [Evidence and approval records](runtime.md#evidence-and-approval-bindings) identify the material covered, applicable attempt, checkpoint or other references, and relevant context. The output commit exists before approval for repository material. Bind records through the CLI in JSON state and audit history. Applicable contracts determine the required scope.
- [Parallel execution](runtime.md#parallel-execution) supports dependency-ready tasks and independent units without shared admission commits or global coordinator `HEAD` gates. At admission, capture the current unit integration commit containing all required predecessor outputs. Keep that baseline for the admitted task. Later commits alone do not invalidate it. Git history or integration provenance establishes inclusion; timestamps alone do not.
- [Integration checks](runtime.md#integration-and-verification) cover the combined unit result. Separate task results do not prove that the combination works. Within the applicable attempt, earlier evidence remains usable only after verifying unchanged covered material and relevant inputs. Authorized revision still requires stage execution and completion conditions again.
- [Checkpoint retention](runtime.md#checkpoint-retention) keeps required Git objects reachable through retained references. External material and separate logs need their own retention rules. Detailed retention, publication, cleanup, and interrupted-work recovery remain open. Workspace and branch layouts are not selected.
- The shared [Artifact metadata contract](metadata.md) defines `id`, `type`, `schema_version`, `unit_id`, `author`, and `labels` as common frontmatter fields. `unit_id` is required for unit-owned artifacts and omitted from project-scoped artifacts. Stage-specific fields remain deferred.
- [Field validation](metadata.md#field-validation) permits only shared fields and extensions defined by the artifact's agreed contract. Unknown fields are errors. Preserve invalid content for correction; do not silently ignore or delete fields. Requester-defined label values remain open under the labels contract.
- [Value validation](metadata.md#value-validation) requires present, non-null required fields, correct types, non-empty strings, both author identity components, and integer schema version `3`. Omit unused optional fields; a present `labels` field must be a non-empty valid string list. Validation is read-only: do not convert types or fill missing values. Creation operations can populate fields explicitly.
- [Metadata change rules](metadata.md#metadata-changes) permit deliberate artifact reclassification, ownership transfer, and label additions or removals. Preserve the artifact UUID and original author. Transfer the owning-unit reference and artifact location together. Validate affected contracts and apply the shared revision rules for completed work.
- Optional [labels](metadata.md#labels) are shared by all artifact types. The vocabulary is open: Kepler can define canonical labels, and the requester can add other labels. Omit the field when empty and do not use labels for execution state. The canonical `walking-skeleton` label on `unit-of-work.md` records the unit's classification without a separate `unit_kind` field.
- [Label validation](metadata.md#label-syntax-and-validation) uses Kubernetes label-key syntax on the existing list of strings: a 1-to-63-character name with optional DNS prefix, no whitespace, case-sensitive matching, and no duplicate strings. This replaces the proposal to permit spaces in requester-defined labels.
- Accepted [artifact types](metadata.md#accepted-type-values) are `unit-of-work`, `functional-design`, `non-functional-requirements`, and `project-reference`. Supporting document types are deferred in DF06; the proposed generic `supporting-detail` value was not accepted.
- Artifact `id` values are CLI-generated UUIDv4 values with cross-project uniqueness. Store the full lowercase hexadecimal value in `8-4-4-4-12` hyphenated form, without prefixes or braces. Do not shorten IDs. They remain stable across content revisions, renames, and moves. Document purpose stays in `type`, not the ID.
- [Unit IDs](unit-of-work.md#identity-and-directory) use `YYYY-MM-DD-<slug>`, with the machine-local date when the CLI creates the unit. They are unique within the project and are the exact directory names. Keep them unchanged across revisions and retries. The CLI must detect duplicate IDs without overwriting an existing unit.
- [`schema_version`](metadata.md#schema-version) uses the Kepler major version. Use the integer `3` for Kepler 3.x. Minor and patch releases must not change it or make valid artifacts invalid. Incompatible changes require a new major version. The CLI reports unsupported schema versions and leaves those artifacts unchanged. Do not migrate data automatically. The migration procedure remains deferred under DF05.
- `author` identifies the original creator as one `Name <email>` string, using Git `user.name` and Git `user.email` at artifact creation. Preserve it during later edits, including edits by another person. Explicit correction of incorrect attribution is permitted. Record later contributions through Git history and audit records. The planned [current-author CLI command](runtime.md#current-author) returns the current project Git identity, not an existing artifact's stored creator. The command name, output format, and missing-value behavior remain open.
- Required documents have required sections. Additional detail lives in linked files under `details/`, not optional inline sections.
- Functional Design supporting files live under `details/functional-design/`.
- The shared [Depth definition](depth.md) uses Minimal, Standard, and Comprehensive levels. Set one unit default with explicit stage overrides. Use Standard when no other level is selected. The agent recommends adjustments; the requester decides.
- Depth controls analysis and documentation detail. It does not remove required information, weaken verification, or prescribe file counts or page lengths.
- The [orchestrator agent](revision.md#authority-and-escalation) decides whether to start a revision cascade and selects its starting stage. Stage agents report findings, evidence, uncertainty, and proposed boundaries. Clarification must preserve existing decisions and requester product authority. Confirmed invalid upstream contracts require revision; cost alone does not justify continuing under them. The orchestrator must address evidence and allow unresolved concerns to be reported again. Ordinary internal correction loops do not require its approval.
- The shared [Revision rules](revision.md) start at the earliest affected stage and execution scope authorized by the orchestrator. Reopen every downstream stage and its artifacts within that scope. Upstream stages remain complete while their contracts and outputs remain valid.
- Each stage contract defines a reopening questionnaire for the shared revision procedure. Answers support the orchestrator's decision; they do not authorize reopening. A questionnaire does not exempt downstream stages from an authorized cascade. Functional Design defines its [questionnaire](phase_construction/functional-design.md#reopening-questionnaire).
- Keep revision authority and safeguards in `revision.md`. Keep attempt rules and [CLI-managed revision decision records](runtime.md#revision-decisions) in `runtime.md`. Record the orchestrator's decision and reason through the CLI in execution state and audit history. Do not add a separate orchestrator document at this point. Construction also defines its task execution responsibilities. Other responsibilities require their own contracts.
