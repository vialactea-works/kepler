# Kepler 3.2.0

This candidate adds verified mission-history recovery and generation-aware workflow coordination. It does not authorize a live recovery, install a client, or migrate existing records automatically.

## Added

- Public `recovery inspect`, `status`, `migrate`, `reset`, `reconstruct`, and `publish` operations with strict requests and explicit mission scope.
- Generation controls, exact-byte archives, manifest-bound operation intents and receipts, private reconstruction drafts, and independent verification before publication. Recovery can inspect invalid history without a healthy old projection.
- Provider-neutral client-compatibility and lead-reconciliation evidence. Recovery checks exact run, working-copy, operation, ownership, and retained-material bindings before effects.
- Exact original-request preservation. Missing originals or corrected conflicting records require the specific unchanged-original assertion and canonical requester statement.
- The optional `kepler-lifecycle-migration` skill and its dated generation-migration guide. The bundle contains fifteen skills and eight host profiles.

## Changed

- Ordinary mission readers select current generation authority before loading phase journals. Mutations carry the caller's captured `--history-version`, hold the mission fence across their effects, and reject stale or recovering selections.
- Working-copy preparation verifies ownership, current material, and settled history. Transfer of an unavailable bound origin requires explicit identities and proof; copying a selector does not grant write authority.
- Reconstruction checks actual typed artifact, task-graph, and repository-checkpoint bytes. Published-prefix checks preserve valid later progress and unit membership without repeating historical approval checks during ordinary reads or joins.
- Recovery and workflow documentation distinguish implementation, operation approval, client activation, and release status.

## Fixed

- Revision cascades bind actual predecessor transitions, including affected child Activities. The writer prevents new unordered cascades; it does not rewrite existing journal history or weaken legitimate ordering failures.
- Reset apply/retry supports exact declared source loss and damaged or missing prior selectors without requiring a healthy predecessor. Unreadable, changed, unsafe, or undeclared inputs remain blocking.
- Target archives encode long resource paths with standard USTAR prefix fields, including the required migration guide. UTF-8 byte limits, checksums, safety checks, and short-path archive bytes remain intact.

## Compatibility

The Construction artifact schema remains version 3. History-control, reconstruction, and evidence formats retain their own version counters. The root package, Core package, CLI package, source release constants, and resource manifest use 3.2.0 together.

Existing direct-phase mission journals are legacy read-only inputs for the new client. Ordinary writes require a valid generation selection. Healthy migration needs a matched released guide. The bundled first guide has `status: released` and `available_in: 3.2.0`. It permits the supported operation only after client checks and exact manifest approval; it does not authorize a migration by itself. Damaged history requires separate reset/reconstruction decisions and complete preservation.

Clients and adapters must satisfy `mission-history-generations/v1`; a version label alone does not prove compatibility. The pinned legacy 3.1.0 build `d2a9f5037c227765818e220443f426303bef4b45` is unsupported. Keep incompatible or unverified clients stopped until an actual compatible implementation and verified preparation permit their return. The generation guard cannot force old executables to comply or detect an outside restart.

Use the matching versioned resource home, profiles, and SDK adapter. Setup does not replace edited resources, install a CLI, or register a host. Package publication, installation, activation, deployment, and each live recovery operation remain separate decisions.
