# Kepler 3.0.0

Kepler 3.0 introduces mission-based software work through the Standard Construction workflow. The CLI, templates, guidelines, skills, and Pi profiles ship together in one versioned archive per target.

## Added

- Missions with explicit requests, selected repositories, and a durable record home.
- A complete six-stage workflow: Functional Design, Quality Requirements, Implementation Planning, Implementation, Unit of Work Review, and Deliver.
- Task graphs with explicit inputs, outputs, acceptance criteria, verification, prerequisites, and dependencies.
- Code Generation, Code Validation, and Code Integration Activities, with task admission and scoped execution attempts.
- Typed assessments, evidence, requester approvals, and history-derived state queries. Diff packages support task validation, Integration, and whole-unit review.
- Mission preparation recovery, acknowledged pause/resume, authorized revision, and guarded Integration acceptance and release.
- Six Construction templates, eleven portable skills, and four Pi-native role profiles.
- A complete mission tutorial and command reference.
- A format-two installation receipt with a guarded format-one transition path.
- An isolated `dev:package` flow that validates a development archive without replacing the stable installation.

## Changed

- One authored version coordinates the CLI, packages, resource manifest, and artifact compatibility.
- The installer downloads one complete target archive, verifies it, and invokes its `kepler setup`.
- Setup alone activates an immutable generation and the stable launcher. It registers one Pi resource package through the generation selector.
- Built-in templates and guidelines remain inside the selected generation. Setup preserves existing settings, custom assets, project data, and prior generations.
- Pi owns resource discovery and loading. pi-subagents owns role loading and worker execution. Kepler records and validates explicit workflow operations.
- Claude Code role definitions remain separate. Pi setup does not install or translate them.

## Fixed

- Interrupted mission preparation continues with the original mission identity instead of creating another mission.
- Task readiness and admission use current, task-scoped prerequisite evidence.
- Stage completion validates the selected artifacts and their recorded provenance.
- Integration acceptance checks the exact prepared candidate and current check evidence. Guarded recovery preserves accepted facts and uncertain effects.
- Setup rejects incomplete archives, mismatched identities, unsupported Pi prerequisites, and conflicting resources before activation.
- Native resource transfer requires review of the exact plan and its digest. Changed, unknown, custom, or mixed resources remain blocked.
- Bootstrap cleanup checks staging-directory ownership and retains failed candidate evidence.

## Compatibility and upgrade notes

- The 3.x line uses artifact `schema_version` 3. Receipt, resource-manifest, event, task-graph, and CLI envelope formats keep separate counters.
- Existing schema-3 artifacts, journals, earlier workbench data, and custom settings remain intact. Setup does not convert earlier change-based workflows into v3 missions.
- The earlier command surface remains under `kepler workbench`. Keep that work with its matching artifact and workflow model.
- Managed Pi setup requires Pi 1.2.0, pi-subagents 0.76.1, an existing agent directory, and initialized settings. Setup does not install those prerequisites, models, or credentials.
- Release targets are Linux and macOS on x86_64 and arm64. The release pipeline tests each target's exact native archive before publication.

## Known limitations

- The implemented phase is Construction. Initialization and Inception are outside this release's workflow scope.
- Code Integration supports one prepared repository per unit, even though mission preparation can select several repositories.
- Construction lint checks supported graph and Markdown-link rules. It does not check path operands inside task verification commands. Review those paths before execution; lint is not a sandbox.
- The host remains responsible for worker execution, independent review, permissions, requester decisions, and model configuration. Resource loading does not certify agent behavior.
