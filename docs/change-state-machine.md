# Kepler change lifecycle and state machine

Kepler does not persist one aggregate change-lifecycle status. The lifecycle is a derived view of the change artifacts, their latest physical records, Git commits and ranges, and the result of the finish precondition. The state names and arrows below are explanatory predicates, **not** new YAML values. Artifact `status` fields remain artifact-specific; `kepler workbench context` classifications and a precondition command's `success` / `negative` / `error` result are reports, not change-level state. ([`context.ts`](../packages/cli/src/workbench/context.ts#L21-L27); [`artifact-types.ts`](../packages/cli/src/workbench/artifact-types.ts#L7-L20); [`precondition.ts`](../packages/cli/src/workbench/precondition.ts#L40-L60))

## Scope and authority

`kepler-init` runs once per project to write or extend `AGENTS.md` and scaffold `.kepler/specs/` and `.kepler/changes/`. For each change, `kepler-plan` is mandatory; `kepler-propose` is optional for a heavyweight specification phase. Every active task then runs through `kepler-code` and `kepler-code-feedback`; after all tasks have fresh approvals, one `kepler-review` assesses the whole branch; `kepler-finish-work` owns final synchronization and delivery. Wayfinder is a separate optional pre-change route process. `kepler-critique` optionally reviews propose artifacts; its disposition selects the next applicable core stage. ([`kepler-init`](../skills/kepler-init/SKILL.md#L11-L64); [`kepler-propose`](../skills/kepler-propose/SKILL.md#L11-L22); [`kepler-critique`](../skills/kepler-critique/SKILL.md#L11-L20); [pipeline overview](./skills.md#L15-L33))

| Authority | Owns | Does not own |
| --- | --- | --- |
| User / change requester | Approves propose artifacts and attended plan breakdowns; disposes of critique findings; resolves user-owned decisions; supplies an explicit whole-change waiver; selects a finish strategy when project standards give no default. | A tool cannot infer these decisions from artifact content or a command flag. |
| Stage skill | The stage's semantic judgment, its owned artifact, and its handoff contract. `kepler-code`, feedback, review, and finish have distinct write scopes. | A skill does not silently assume another stage's ownership. Review skills judge; they do not repair implementation. |
| Workbench CLI | Artifact parsing and lint, context reporting, diff/checkpoint mechanics, and the concrete finish-precondition checks described below. | It does not decide whether a design is good, whether the review actually covered its scope, whether an explicit waiver was authorized, or whether a remote effect is real. |
| Person or `kepler-orchestrate` | Runs the sequence, interprets durable evidence, resumes the earliest unresolved task, and dispatches the next owning skill. | `kepler-orchestrate` does not implement, edit stage-owned evidence, merge, open a request, or run finish-work; it hands off after whole-branch approval. |

The skills express semantic and sequencing requirements; the workbench supplies workflow mechanics. A lint pass is not readiness, and a passing precondition is not proof that a human-approved design, semantic review, or remote effect is correct. ([`kepler-orchestrate`](../skills/kepler-orchestrate/SKILL.md#L1-L19); [`docs/skills.md`](./skills.md#L41-L72); [`kepler-review`](../skills/kepler-review/SKILL.md#L100-L126); [`kepler-finish-work`](../skills/kepler-finish-work/SKILL.md#L71-L112))

## Artifact paths and field glossary

The change directory is `.kepler/changes/<change>/`. Canonical specs live separately in `.kepler/specs/`; they state current behavior, while `requirements/` holds change-side deltas. The owning skill and the template define each artifact's write boundary. ([artifact layout](./skills.md#L351-L399); [templates](../bundle/templates/))

| --- | --- | --- | --- |

Frontmatter means only the YAML block between `---` delimiters. Headings and labels above belong to the Markdown body even when parsers treat them as structured evidence. The reader separates those regions; schemas enumerate required metadata and allow additional properties, while body validators parse task ledgers, attempts, and review passes. Do not move body labels such as `Outcome`, `Base`, `Head`, or `Verdict` into invented YAML fields. ([`artifact-reader.ts`](../packages/cli/src/workbench/artifact-reader.ts#L35-L40); [`artifact-types.ts`](../packages/cli/src/workbench/artifact-types.ts#L178-L318); [`artifact-schemas.ts`](../packages/cli/src/workbench/artifact-schemas.ts#L48-L139); [`artifact-body.ts`](../packages/cli/src/workbench/artifact-body.ts#L265-L280))

Status names are not interchangeable. In particular, root `progress.md` frontmatter `status` has its own schema (`pending`, `in-progress`, `blocked`, `complete`); task rows use `done`, and task-local progress uses its own status. The precondition validates the root metadata schema but does **not** require root `progress.status: complete`; it requires every active task row and linked task artifact to be done. A feedback/review artifact's frontmatter `status` and `decision` are not its latest pass verdict. Modern histories use pass-local body `Verdict:`. In accepted legacy-global histories, the parser binds frontmatter `base`, `head`, and `verdict` only to the physical last legacy pass; structural earlier records cannot supply an approval. A transitioned history uses its explicit pass-local suffix, never an older global approval. ([`artifact-types.ts`](../packages/cli/src/workbench/artifact-types.ts#L178-L318); [`artifact-body.ts`](../packages/cli/src/workbench/artifact-body.ts#L686-L840); [`precondition-artifacts.ts`](../packages/cli/src/workbench/precondition-artifacts.ts#L112-L253))

Active tasks are the ordered `### Task N: <title>` records in `plan.md`, excluding only titles ending in the complete `(abandoned — <nonempty reason>)` form. Keep abandoned task numbers, directories, and history; remove their rows from the active root ledger. A plan can retain only abandoned tasks with `tasks: []` and an empty root body ledger. That skips task implementation and feedback, but still requires whole-branch review and every other finish gate. ([abandonment contract](../skills/kepler-plan/SKILL.md#L278-L283); [`taskTitleAbandoned`](../packages/cli/src/workbench/precondition-artifacts.ts#L109-L110); [zero-active-task test](../tests/workbench/precondition.test.ts#L527-L537))

## Derived change states

The diagram names states for readers; none is a new persisted field. “Latest” means the physically last parsed attempt or pass, not the most favorable prior entry. Task, feedback, review, and finish artifacts keep their own records. ([`review-passes.ts`](../packages/cli/src/workbench/review-passes.ts#L772-L936); [`artifact-body.ts`](../packages/cli/src/workbench/artifact-body.ts#L514-L573))

```mermaid
stateDiagram-v2
    [*] --> ProjectReady: kepler-init, once per project
    [*] --> DanglingAttempt: resume a persisted unmatched finish Attempt
    ProjectReady --> PrePlan: create a change
    PrePlan --> Proposed: optional kepler-propose; requester approves artifacts
    PrePlan --> Planned: tactical change skips propose; kepler-plan
    Proposed --> Planned: kepler-plan
    Proposed --> UpstreamRevision: accepted critique requires intent revision
    Planned --> TaskUnresolved: an active task remains
    Planned --> AllTasksGated: no active tasks remain

    TaskUnresolved --> TaskUnresolved: blocked or interrupted; resolve same task
    TaskUnresolved --> FeedbackPending: kepler-code records done attempt and commit
    FeedbackPending --> TaskUnresolved: fresh changes-requested; ordinary code findings
    FeedbackPending --> RiskAdjudication: fresh changes-requested; canonical cannot-verify blocker
    RiskAdjudication --> TaskUnresolved: driver confirms a code gap
    RiskAdjudication --> FeedbackPending: located evidence; feedback on unchanged Base and Head
    RiskAdjudication --> RiskAdjudication: unresolved risk; no advancement
    FeedbackPending --> FeedbackPending: absent, skipped, invalid, or stale pass; obtain fresh feedback
    FeedbackPending --> TaskApproved: durable, fresh approved feedback
    TaskApproved --> TaskUnresolved: another active task remains
    TaskApproved --> AllTasksGated: every active task is approved

    AllTasksGated --> WholeReviewPending: no cleared review; latest verdict selects C6 review or C7 findings
    AllTasksGated --> WholeReviewApproved: reuse existing durable approval with a valid current-branch range
    WholeReviewPending --> WholeReviewApproved: kepler-review commits a valid approved pass
    WholeReviewPending --> TaskUnresolved: implementation findings; re-plan remediation tasks
    WholeReviewPending --> UpstreamRevision: finding invalidates approved intent
    WholeReviewApproved --> WholeReviewPending: driver requires a new review for material-stale coverage
    UpstreamRevision --> Proposed: revise and approve affected artifacts
    UpstreamRevision --> Planned: approved revision changes the task plan
    UpstreamRevision --> WholeReviewPending: approved revision leaves implementation plan valid

    WholeReviewApproved --> FinishAdmitted: E0-E10 and skill policy pass, including E9 fresh-or-waived
    WholeReviewApproved --> FinishGateClosed: any admission predicate fails
    FinishGateClosed --> FinishGateClosed: repair failed predicate and recompute
    FinishGateClosed --> WholeReviewPending: unwaived material coverage requires a new review
    FinishGateClosed --> FinishAdmitted: all admission predicates pass
    FinishAdmitted --> SpecSync: capture gate-entry state
    SpecSync --> UpstreamRevision: required delta missing or approved inputs disagree; no Attempt
    SpecSync --> AttemptCommitted: specs synchronized or verified unchanged; Attempt N committed
    AttemptCommitted --> FinishEffects: verified boundary; optional route transition and selected strategy
    AttemptCommitted --> DanglingAttempt: interruption before matching Outcome is persisted
    FinishEffects --> WholeReviewPending: unowned post-gate mutation; stop, persist blocked Outcome if safe
    FinishEffects --> FinishCompleted: all intended effects read back; Outcome N persisted
    FinishEffects --> FinishBlocked: failure or partial effect read back; blocked Outcome N persisted
    FinishEffects --> DanglingAttempt: interruption before matching Outcome is persisted
    DanglingAttempt --> FinishCompleted: reconcile actual effects and persist completed Outcome N
    DanglingAttempt --> FinishBlocked: reconcile failure or stable partial state; persist blocked Outcome N
    DanglingAttempt --> FinishEffects: same Attempt can safely continue from first unverified step
    DanglingAttempt --> DanglingAttempt: ambiguous or unsafe state; stop without mutation
    FinishBlocked --> WholeReviewApproved: later retry revalidates evidence before a new gate and Attempt
    FinishCompleted --> [*]
```

No diagram label is persisted. A direct successful admission does not require a preceding gate failure. Resume reuses current approvals rather than manufacturing another pass; a dangling finish Attempt takes the recovery path before any new gate or attempt allocation.

### State meanings

- **ProjectReady** is the one-time `kepler-init` output: standards and `.kepler/{specs,changes}/` exist.
- **PrePlan / Proposed / Planned** distinguish an unplanned change, optional approved proposal context, and a required plan plus initialized root ledger and task logs.
- **TaskUnresolved** means the earliest active task is pending, blocked, interrupted in-progress, or returned for correction. **FeedbackPending** means its implementation is marked done but it has no durable fresh approval. **RiskAdjudication** holds a fresh `changes-requested` pass with a canonical unresolved evidence blocker. **TaskApproved** requires completion plus durable fresh approved feedback; a root `done` row alone is insufficient.
- **AllTasksGated** requires every active task done with durable fresh approved feedback; an empty active-task set satisfies only this task predicate. **WholeReviewPending** means a review must be created, corrected, or repeated. **WholeReviewApproved** identifies a valid, durable, approved latest pass without Blocking findings whose range is on the current branch. It does not itself assert material coverage: E9 separately requires freshness or the explicit narrow waiver. The ordinary orchestrator hands off only a material-fresh approval; a requester can authorize the finish skill's waiver path without waiving the other gates.
- **FinishGateClosed** is a transient computed result, not finish history. **FinishAdmitted** means history preflight, the CLI's `gate: open`, and the skill-owned requirements all pass. No finish Attempt exists yet. **SpecSync** precedes attempt allocation. **AttemptCommitted**, **FinishEffects**, and **DanglingAttempt** depend on durable finish history and Git/external observations.
- **FinishCompleted** and **FinishBlocked** derive from a paired persisted Attempt/Outcome and verified result. A blocked Outcome is not a completed change; a later try revalidates current evidence and passes a new gate before allocating a new Attempt.

`FM` means YAML frontmatter; `body` means parsed Markdown headings, table cells, or labels. The transition controller owns the effect in its row. “Driver” means the person or `kepler-orchestrate`; the skills themselves do not invoke one another. A failed guard leaves no later-stage authorization. ([stage ownership and loop](./skills.md#L400-L414); [`kepler-orchestrate`](../skills/kepler-orchestrate/SKILL.md#L204-L315))

## Exact finish-work admission predicate

Finish admission is the conjunction of history preflight, the CLI predicates, and skill-owned requirements. The CLI evaluates checks in order and accumulates failures; it does not stop at each false predicate as a short-circuit state engine would. The skill runs scoped lint before invoking the precondition command; the CLI itself does not call `kepler workbench lint`. Only after `gate: open` may spec synchronization and finish history begin. A pre-gate failure creates no `finish.md` Attempt or Outcome. ([`kepler-finish-work` preconditions and process](../skills/kepler-finish-work/SKILL.md#L71-L112); [`PreconditionService.execute`](../packages/cli/src/workbench/precondition.ts#L70-L155); [`LintService`](../packages/cli/src/workbench/lint.ts#L281-L398))

```text
CLI_OPEN = E1 AND E2 AND E3(exit 0) AND E4 AND E5 AND E6(parsed)
           AND E7(CLI) AND E8(CLI) AND E9 AND E10
FINISH_ADMITTED = E0 AND CLI_OPEN AND skill_policy
E9 = material_commit_exists AND
     (material_commit_is_ancestor_of_review_Head OR material_ancestry_waived)
```

`skill_policy` includes selecting the full suite and build/typecheck, exactly one well-formed latest done outcome per active task, no unresolved evidence blocker, and explicit user authorization if the waiver flag is used. The CLI cannot prove those semantic facts. Lint validates existing files; it does not supply missing evidence required by E5–E8. E0 and the policy are skill checks, not additional checks inside `PreconditionService`.

| Edge | Condition to pass | Exact reads / enforcement | If false |
| --- | --- | --- | --- |
| E0 — history preflight | For a new attempt, run `kepler workbench lint --change-dir <change-dir>` and require success. If `finish.md` exists, lint it before preconditions; if it ends in an unmatched Attempt, reconcile that attempt first. | Scoped lint validates recognized artifact schema/body. The finish skill inspects history; `PreconditionService` does not read `finish.md`. | Stop before a new precondition/Attempt; report lint findings or reconcile the dangling attempt. |
| E1 — target and command | CLI options `--change-dir` and `--test-cmd` are supplied; the test command is nonempty. The effective resolved change directory exists and lies strictly below its Git repository root. | The service resolves the supplied path against runtime cwd before target validation, so an empty raw directory string is not universally rejected. CLI runs `bash -c <testCommand>` at the resolved repository root. | CLI error result (exit 2); no finish history. |
| E2 — clean at entry | `git status --porcelain` is empty. | CLI clean-tree check before verification. | Gate closed; no finish history. |
| E3 — verification command passes | Supplied command exits `0`. The skill obtains both the full test-suite and build/typecheck commands from `AGENTS.md` and passes a command that runs both. In this repository, that is `bun --bun vitest run && bun run build` ([`AGENTS.md`](../AGENTS.md#L5-L15)). | CLI executes one supplied shell string and trusts its exit code; it does not parse the command to prove that it includes the full suite or a build. | Gate closed; fix verification and rerun. |
| E4 — clean after verification | `git status --porcelain` remains empty after the command. | CLI checks the tree after test/build command. | Gate closed; clean generated/uncommitted changes and rerun. |
| E5 — plan and root ledger durable and matching | `plan.md` and root `progress.md` are tracked/committed at `HEAD` and satisfy artifact contracts. Plan body `# Plan: <title>` and active `### Task N: <title>` records match root progress table by count, order, number, and exact title. | CLI checks HEAD blob equals worktree content and there is no staged diff for each; it does not require these two paths' latest commits to be path-only. Root `progress.tasks[]` must match row count and each row's `id`, exact title, status, `tasks/task-N/progress.md` path and exact `[details](...)` link. Every active task row is `done`. The top-level `progress.status` is schema-validated but need not be `complete`. | Gate closed; repair plan/ledger using its owner, then re-evaluate review freshness if a material commit changed. |
| E6 — each task implementation outcome | For each active Task N, linked task progress artifact is present, valid, and has matching frontmatter `task` and `change`; task-progress frontmatter `status` is `done`; its physically latest `## Attempt N` has body field `Outcome: done`. | CLI reads the latest parsed attempt's `Outcome`. It does not apply `exactArtifactCommit` to task-progress. The skill additionally requires one well-formed latest done outcome and checks task evidence; the CLI parser's map overwrites duplicate fields and explicitly accepts historical unbulleted `Outcome: done`, so CLI alone does **not** enforce the skill's “exactly one” rule. ([`artifact-body.ts`](../packages/cli/src/workbench/artifact-body.ts#L265-L280); [compatibility test](../tests/workbench/precondition.test.ts#L453-L488)) | Gate closed; return to the task owner. Do not fabricate a done attempt. |
| E7 — every task feedback pass | For each active task, the physical latest feedback pass matches `Task N — <exact Task N title from plan.md>`, has `Verdict: approved` and no Blocking finding, is durable at `HEAD`, and its latest touching commit contains only that feedback path. Full lowercase 40-character Base and Head resolve; Base is ancestor of Head; Head is ancestor of current `HEAD`. | CLI checks identity, pass validity, durability, and range. It requires the latest task-progress commit to be an ancestor of feedback Head when it resolves that commit as a full SHA; task-progress itself does not receive the path-only durability check. The skill requires verifiable latest task evidence and no canonical unresolved `cannot verify from diff` Blocking item. | Gate closed on a failed CLI check; otherwise any failed skill requirement still prohibits finish. Rerun feedback or route confirmed code findings to the same task; a later task attempt stales its prior approval. |
| E8 — whole-branch review pass | Root review body title exactly matches the plan title; physical latest pass is valid, `Verdict: approved`, and has no blocking finding. The review file is durable and its latest touching commit is review-only. Base and Head are full resolvable commit IDs; Base is ancestor of Head; Head is ancestor of current `HEAD`. | CLI checks path-specific durability and range ancestry. `kepler-review` separately requires Base to equal the actual merge base against the target/default branch; precondition does **not** resolve the target or recompute merge base. | Gate closed; re-review or repair invalid evidence. Never fall back to an earlier approval. |
| E9 — whole-change material freshness | A material commit exists on the current branch, and either it is an ancestor of latest whole-review Head or the material-ancestry flag is set with explicit user authorization. | Material lookup excludes root `progress.md`, `review.md`, `finish.md`, and active task progress/feedback paths. The flag skips only this material-coverage comparison. | Unwaived material-stale coverage closes the gate. The waiver never admits missing material, malformed/unresolvable/off-branch ranges, invalid or nonapproved review, undurable evidence, or any other failed predicate. |
| E10 — final clean tree | After all prior predicates pass, `git status --porcelain` is still empty. | CLI performs a final clean-tree check only when earlier gates have no failures. | Gate closed; no Attempt. |
| E11 — admission | E0, CLI_OPEN, and skill_policy all pass. | CLI emits `gate: open` only for E1–E10; the finish skill also enforces E0 and its semantic requirements. This is computed authorization, not persisted lifecycle metadata. | Report the applicable blocker verbatim and make no new-attempt finish-stage write. |

The waiver is narrow and intent-bearing: the CLI accepts a boolean flag and cannot establish who authorized it. The skill requires an explicit user waiver, records it in the Attempt, and does not let it bypass ledger, feedback, review validity/verdict, range ancestry, cleanliness, or test/build checks. Similarly, a passing gate does not make an invalid finish input acceptable. ## Task implementation and feedback loop

For one exact active Task N, code uses `tasks/task-N/.base` as the fixed pre-implementation checkpoint. The first checkpoint may be recorded at current `HEAD` only when the row is `pending`, no task attempt or feedback exists, and there is no task-owned implementation work. After durable evidence exists, reuse or reconstruct only the original checkpoint from unambiguous evidence; never replace it with the current `HEAD`. The coder changes only its assigned root row and task log, performs the plan's Red → Green → Refactor sequence, verifies, and commits implementation plus task evidence. A graceful blocker is an explicit `Outcome: blocked`; abrupt interruption leaves the row `in-progress` with no invented attempt. ([`kepler-code` TDD and process](../skills/kepler-code/SKILL.md#L58-L231); [`kepler-orchestrate` checkpoint recovery](../skills/kepler-orchestrate/SKILL.md#L32-L112))

Feedback reviews the full stable task range, but does not edit code, task status, or task progress. It appends to the one `feedback.md` history and commits only that file. Ordinary fresh `changes-requested` findings send the same task back through a verified correction cycle; a canonical unresolved `cannot verify from diff` Blocking item first enters driver adjudication (C4a). Located evidence can instead justify re-feedback on unchanged Base/Head without a code commit; `approved` authorizes advancement only after the driver verifies durable commit and freshness. Missing, skipped, invalid, or stale evidence asks for feedback again. The physical latest pass is authoritative: a malformed latest pass cannot revive an older approval. ([`kepler-code-feedback`](../skills/kepler-code-feedback/SKILL.md#L93-L229); [`kepler-orchestrate` task resume matrix](../skills/kepler-orchestrate/SKILL.md#L113-L183); [`review-passes.ts`](../packages/cli/src/workbench/review-passes.ts#L772-L936))

A task feedback range is fresh only if its Base/Head are full valid commits, Base is an ancestor of Head, Head is an ancestor of current `HEAD`, and Head contains the latest commit touching that task's progress file. Thus a new attempt on that task makes its earlier feedback stale, including an earlier `changes-requested` pass. Evidence-only re-feedback may use the same range only when located evidence resolves a named `cannot verify from diff` blocker; otherwise correction requires new implementation and verification. ([`kepler-orchestrate` durable task approval and matrix](../skills/kepler-orchestrate/SKILL.md#L113-L183))

## Whole-branch review and repair

Whole-branch review begins only after every active task has durable fresh approved feedback. `kepler-review` must compute the actual merge base against the target/default branch and inspect the complete range, affected consumers, cross-task composition, missing material changes, tests, security, and repository assumptions. It appends to root `review.md` and commits only that artifact. An approved review is fresh only while its Head contains the latest material change commit and remains an ancestor of current `HEAD`. ([`kepler-review` range and preflight](../skills/kepler-review/SKILL.md#L19-L99); [inspection and focused verification](../skills/kepler-review/SKILL.md#L100-L174); [freshness](../skills/kepler-review/SKILL.md#L237-L250))

If the physical latest review requests implementation changes, `kepler-orchestrate` routes the complete finding set to `kepler-plan` re-plan mode. Re-plan adds numbered remediation tasks without rewriting completed task definitions or histories; each remediation uses the same code/feedback loop before a new whole review. If a finding invalidates approved requirements or design, return to proposal/artifact revision and approval instead of designing around it in code. The driver reuses an existing fresh approval rather than rerunning it. A later material edit requires fresh review for finish admission unless the requester explicitly waives only that material-ancestry comparison; neither a waiver nor reuse relaxes range validity or the same-attempt mutation boundary. ([`kepler-orchestrate` whole-review matrix and findings](../skills/kepler-orchestrate/SKILL.md#L186-L315); [`kepler-plan` re-plan mode](../skills/kepler-plan/SKILL.md#L212-L330))

## Finish history, synchronization, and recovery

The precondition gate does not read `finish.md`. The finish skill owns it after admission. On a first admitted attempt, finish-work syncs canonical specs from approved change deltas, validates each changed spec, and commits only derived spec paths (or verifies `HEAD` unchanged when no spec change is needed). It does not invent canonical behavior from code, progress, or review comments. Validate approved inputs where present; optional proposal, design, and deltas need not exist on a tactical change. Without deltas, compare touched capabilities against current specs: unchanged behavior permits a verified no-spec-change result, while changed behavior requires a missing-delta stop. Incorrect requirements or inconsistent approved inputs also abort before Attempt allocation or canonical-spec commit, returning to artifact revision and fresh whole review. ([`kepler-finish-work` specification synchronization](../skills/kepler-finish-work/SKILL.md#L113-L167))

`finish.md` holds one append-only paired history. Each pair uses `## Attempt N — date` and `## Outcome N — date`; numbering is strictly monotonic, each number appears once per kind, and an Outcome must match its Attempt. The Attempt records the admitted gate, spec synchronization, selected strategy, intended workspace result, and route intent. The skill commits that Attempt before the first route or finish effect. Only after reading back actual state does it append and commit the matching Outcome as completed (all intended effects verified) or blocked (failure or stable partial state). Attempt and Outcome are separate commits because the effect is not known when intent is recorded. ([`finish.md` template](../bundle/templates/finish.md#L1-L28); [`kepler-finish-work` history](../skills/kepler-finish-work/SKILL.md#L168-L197))

Before allocating a new attempt, finish-work lints existing history. If physical history ends in Attempt N without Outcome N, it first inspects commits/refs, remote branch, request state, route files, and workspace state. If the intended result already occurred, it records the matching completed Outcome; if a stable failure/partial result exists, it records blocked; if the action demonstrably did not start or is safe to continue, it resumes the same Attempt at the first unverified step after rechecking the Attempt commit and mutation boundary. Ambiguous state is left untouched for intervention. Never allocate a duplicate attempt. Lint permits an unmatched Attempt only as the current pending intent (`status: pending`, `result: pending`); that lint-valid shape is a recovery signal, not permission to start a second attempt. ([`kepler-finish-work` resume and recovery](../skills/kepler-finish-work/SKILL.md#L198-L221); [`artifact-body.ts`](../packages/cli/src/workbench/artifact-body.ts#L514-L573))

The same attempt owns only its canonical spec synchronization, exact named route/map changes, and its own numbered finish-history mutations. Those expected changes do not stale that attempt. Changes to `proposal.md`, `design.md`, or `requirements/`, other unexpected paths, amended reviewed commits, or unexplained dirty state abort the next effect and return the change to whole review. The material-ancestry waiver does not widen this allowlist. ([`kepler-finish-work` post-gate mutation boundary](../skills/kepler-finish-work/SKILL.md#L222-L238))

### Finish strategies and verified outcomes

- **`local-merge`:** From the main checkout, merge the change branch (including the Attempt and route commits) into the resolved base branch. Remove the worktree/delete the change branch only when project workflow calls for it. Read back the base ref, merge result, and any intended worktree removal; persist Outcome on the surviving base branch. Verify its commit and pair there, and verify the remote base if the workflow pushes it.
- **`pull-request`:** Push and verify the change branch, open the request, then read back its canonical URL, open state, head, and base from the provider. Leave branch/worktree in place. Commit Outcome on the change branch, push, and verify the remote branch and request head include it. A local-only Outcome is blocked, not completed.
- **`no-op`:** Do not merge, push, create a request, delete a branch, or remove a worktree. Verify the branch/worktree remain and any route intent is committed. Persist Outcome on the unchanged change branch, then reread branch, worktree, route, and paired history.

All three paths require observed readback; command success alone is insufficient. If a command fails after finish effects begin, stop forward actions and inspect actual partial state before writing a blocked outcome. ([`kepler-finish-work` strategy execution and partial failure](../skills/kepler-finish-work/SKILL.md#L284-L329))

Route effects are optional and apply only when `route_unit` identifies a unit. The route template stores unit ID, name, status, dependencies, and backing tickets in frontmatter; the synthesized route body is not rewritten. Finish changes only the named unit from `in-progress` to `shipped` and moves the map from `shipping` to `shipped` only after every unit is verified shipped. Lint, commit, and read back each exact route/map mutation. A change without route backing records no route mutation. ([route template](../bundle/templates/wayfinder/route.md#L1-L40); [`kepler-finish-work` route and strategy process](../skills/kepler-finish-work/SKILL.md#L239-L283); [`map template`](../bundle/templates/wayfinder/map.md#L1-L20))

## CLI enforcement versus skill and user policy

| Check or decision | Enforced by CLI | Skill / user responsibility |
| --- | --- | --- |
| Artifact format | `kepler workbench lint` validates selected recognized artifact contracts; precondition independently parses its required plan, progress, task-progress, feedback, and review artifacts. | Skills run scoped lint at required mutation boundaries and resolve findings. Lint does not prove Git freshness, semantic approval, tests, or finish readiness. |
| Clean tree and test process | Precondition runs clean-tree checks before and after the supplied command, then a final check on otherwise passing gates; it executes `bash -c <test-cmd>` at repo root and checks exit `0`. | `kepler-code` runs task Verify and full tests/build per `AGENTS.md`; finish-work must supply both full suite and build/typecheck commands. CLI does not inspect command contents or add a separate build gate. |
| Ledger and latest evidence | Precondition checks plan/root ledger relationships, task status, latest task outcome, feedback and review identity/verdict/range/durability, and material ancestry. | Skills own the TDD evidence, semantic review quality, branch merge-base correctness, and explicit resume rules. CLI's task-outcome map does not enforce exactly one `Outcome: done` label. |
| Waiver | CLI's boolean `--whole-change-waived` skips only the material-commit-ancestor-of-review-Head test. | The finish skill requires an explicit user waiver, records it, and refuses to infer intent. |
| Specs, routes, finish strategy | CLI precondition does not synchronize specs, change route status, pick a strategy, merge, push, create a request, or remove a worktree. | `kepler-finish-work` validates approved input consistency, syncs specs, enforces same-attempt ownership, asks when strategy has no default, executes one strategy, and verifies workspace/remote/provider readback. |

The review skill's exact-merge-base rule is stronger than the precondition's range check: precondition verifies Base→Head and Head→current `HEAD` ancestry, but does not resolve a target branch or calculate the actual merge base. Likewise, the CLI cannot establish that a reviewer inspected every affected consumer or that an explicit waiver came from the user. These remain skill- and user-governed parts of the contract.
