# Agent-owned Standard operations

Use this file with the owning skill for the selected stage. The [packaged Standard CLI walkthrough](standard-cli-walkthrough.md) contains complete typed JSON request construction for all six stages, task Activities, audits, Integration, and a local repository handoff. It is a controlled one-task example, not a form to replay: replace every identity, input, path, material hash, checkpoint, review, check result, actor, and request decision with facts from the current unit. Never fabricate approvals or successful checks. For different scopes or outcomes, inspect the current CLI's validators and help; report missing contracts instead of guessing. `--request` is strict JSON for lifecycle operations, while `audit record` and `revise` consume strict JSON on stdin. Do not put a JSON filename where the command requires JSON content.

## Select and inspect

1. Confirm the selected CLI/version-specific resource home and that this entire package is loaded by the host. Check the host's worker and independent reviewer capabilities before promising Implementation or Review. Avoid duplicate skill copies.
2. Take the exact record home, mission ID, unit ID, stage, task ID and attempt IDs from creation results, `unit list`/`unit show`, `stage show`, `task show`, `activity show`, and `audit list`/`audit show`. There is no mission list/show/run or global status command. Ask when multiple units match; do not infer a unit from the branch or the chat transcript.
3. Inspect prior status and recorded events before any mutable operation. Reconstruct lost inputs from the exact original start event; keep the same unended attempt when safe. A successful command exit means the command was accepted, not that a check ran, a worker started, or the outcome happened.
4. Check Git and artifact bytes before and after each relevant operation. Preserve existing work; use the repository's configured signing. Never edit `.kepler/` histories, projections, or attachments to repair a guard failure.

## Record only real facts

- Mission creation takes a camelCase request (`title`, `request`, `workflow: "standard"`, `recordHomeRepositoryId`, `contexts`, `repositories`); its response uses snake_case. `unit create` uses the actual returned mission ID and creates no stage. See the complete startup request in the walkthrough's “Create the mission and unit” section. On uncertain startup, reconcile and use `mission prepare`, never repeat `mission create` blindly.
- For an eligible stage, `stage start` takes `{"inputs":[{"reference":"<actual-input>","purpose":"<actual-purpose>"}]}`. Save the returned attempt ID and exact inputs. For resume, use those same pairs with the same acknowledged paused attempt; a pause request does not stop the worker, and an acknowledgement requires confirmed termination and reconciled effects.
- Author current artifacts using the matching packaged templates. Preserve their UUID and author when revising; use `kepler git author`, `kepler uuid`, actual SHA-256 bytes, and repository-qualified committed checkpoints. Lint and self-review before recording evidence. Perform any requested external review in a distinct context. Record actual check names, executor, inputs, `artifact_bindings`, `checkpoints`, result status and output references with `audit record evidence` on stdin. Evidence IDs and event IDs have different uses; keep both from the result.
- Ask for actual requester approval of the exact committed Functional Design and Quality material; only after the explicit decision record `audit record approval` with requester, inputs, bindings, checkpoints, and decision reference. A design or quality approval does not authorize implementation, publication, or deployment. Planning/Review/Deliver approval is conditional on requester or project authority; do not insert a blanket gate.
- Construct each stage completion request from the owning stage's actual assessment and evidence. The walkthrough includes complete examples for all six stages. Keep its field names, expected check names, conditional reviews and approval shape, original source and current delivery checkpoints separate. Inspect `stage show` again before completion. If the current material differs, obtain applicable new evidence/approval instead of reusing a stale receipt.
- Implementation: check the graph and readiness, admit only eligible tasks with actual prerequisite proof, and use separate Generation and non-author Validation workers. A task has three Activities, not three extra stages. The orchestrator alone coordinates Integration; under the unit lock bind the actual captured inputs and checked candidate, run the plan's exact typecheck/build/full suite, record actual results with `integration evidence`, and accept only the unchanged candidate. Activity acceptance and completion remain separate. Review checks the complete unit against its original Review baseline; it does not automatically repeat every full-suite check.
- Deliver: ask for the exact outcome, destination and recipient and record the requester interaction. Outcome selection alone does not authorize external effects. Author delivery instructions, verify authority for each operation, perform only authorized effects, read back real results, and record verification and handoff; complete only when the requested outcome holds. A local repository handoff is not an implicit substitute for a requested deployment.

## Failure and handoff

If a command fails, read its structured `code`, `details`, and `recovery`, inspect partial effects and actual host worker status, and re-query the owning scope. Preserve locks while ownership is uncertain. Never infer an operation did not happen because a response or session disappeared. For an upstream change, coordinate worker stop and lock reconciliation before an authorized revision; Integration-only retry keeps the same attempt. Use `kepler-resume` for cross-stage triage and hand the work back to its owner.

After each developer-facing skill, report selected scope and current state, actual artifacts and evidence, remaining blockers, any decision needed, and one copyable prompt naming the next skill. Keep CLI requests and IDs available to agents without asking the developer to shuttle JSON or run commands. Do not start the next stage just because you completed the current one.
